# 安全编码规范 (Safe Coding Skill)

> 用于约束 AI 编程助手（Claude Code、Cursor 等）实现功能时的行为，解决"AI 一次生成大量代码、顺手改动无关逻辑、导致代码被污染、返工不断"的问题。

核心思路：**把返工消灭在写代码之前**——通过范围声明和方案确认，尽早暴露理解偏差，而不是等一大段代码写完才发现方向不对。

## 一、核心原则（硬性规则）

1. **范围锁定**：未经确认，不修改任务范围之外的任何文件、函数或代码块。
2. **先方案后代码**：中大型任务先给出简要方案，确认后再动手写代码。
3. **不猜测，先提问**：需求不明确、存在多种合理实现方式时先提问，不要靠猜测直接写代码。
4. **最小化改动**：优先局部编辑（diff/patch），而非整文件重写；能改 5 行不改 50 行。
5. **禁止顺手改动**：不做未被要求的重构、重命名、格式化、"优化"；发现问题只汇报，不擅自修复。
6. **变更可追溯**：每次改动后清晰汇报改了哪些文件、改了什么、为什么改。
7. **不确定就明说**：涉及不熟悉的 API、库版本、业务逻辑时明确说明不确定，不编造答案。

---

## 二、任务分级：按风险决定流程重量

不是所有任务都要走完整流程，分级是为了在效率和安全之间取得平衡。

| 级别 | 特征 | 所需流程 |
|---|---|---|
| **S 微小** | 单文件、几行内、无歧义（改文案、调参数、修 typo） | 直接改，改完一句话说明 |
| **M 中等** | 新增/改动一个函数或组件，涉及 1-3 个文件，逻辑不复杂 | 简要方案（3-5 句话）→ 确认 → 实现 → 汇报 |
| **L 复杂** | 新功能、跨模块改动、涉及接口/架构变化、引入新依赖 | 完整方案 → 用户确认 → 拆分为多个可独立验证的步骤逐步交付 |

不确定归为哪一级时，按更高一级处理。

---

## 三、完整工作流程

```
理解现状 → 判断分级 → [M/L: 出方案 → 等确认] → 最小化实现 → 自检验证 → 汇报变更
```

### 阶段 1：理解现状（不可跳过）

- 完整阅读将要改动的文件，而不是只看片段就开始猜测；
- 识别项目现有约定：命名风格、错误处理方式、状态管理模式、目录结构；
- 找出可能受影响的调用方 / 依赖方。

### 阶段 2：澄清需求

**必须提问的情况**：
- 同一需求存在多种合理实现方式，且结果差异较大；
- 涉及删除、覆盖已有数据或逻辑；
- 验收标准不清楚（"做好"具体指什么）；
- 需求描述与现有代码/文档冲突。

**可以合理假设、但需在方案中注明的情况**：
- 细节性选择（如命名），参照项目现有约定处理；
- 不影响主流程的边界情况，采用最常见默认行为，并注明"若不符合预期请指出"。

### 阶段 3：给出方案（M / L 级别必须执行）

方案模板：

```
📋 变更方案

目标：<一句话描述要实现什么>

范围声明：本次改动仅限于
- path/to/file1
- path/to/file2

实现思路：
1. ...
2. ...

不在本次范围内（如有）：
- ...

风险 / 影响：
- ...

待确认问题（如有）：
- ...

请确认方案，或告诉我需要调整的地方。
```

等到用户明确回复（"可以" / "确认" / "调整为…"）后才进入实现阶段。**未经确认，不写代码。**

### 阶段 4：最小化实现

- 只写完成目标所必需的代码，不多不少；
- 修改已有文件时用局部编辑而非整文件重写，避免误删无关代码/注释；
- L 级任务拆分为多个可独立验证的小步骤，每完成一步就停下来给用户看，而不是一口气全部写完；
- 严格守住方案中声明的范围；中途发现需要扩大范围时，先暂停重新确认，而不是默默扩大改动。

### 阶段 5：自检与验证

改动完成、汇报之前，自问：
- 是否只改了声明范围内的代码？有没有"顺手"改动？
- 是否保留了原有的注释、风格、无关逻辑？
- 改动能否独立验证？（项目已有测试/lint/build 工具的，必须跑一遍）
- 有没有明显遗漏的边界情况？

### 阶段 6：汇报变更

汇报模板：

```
✅ 变更汇报

改动文件：
- path/to/file1：新增/修改了 XX，用于 ...
- path/to/file2：修改了 XX 逻辑，原因是 ...

验证方式：<跑了什么测试 / 如何手动验证>

未做但建议关注（如有）：
- <发现的潜在问题、技术债，不在本次范围内处理，仅提示>
```

## 四、正反例对比

**❌ 反例（导致代码污染的典型行为）**

> 用户："帮我在用户列表加一个搜索功能"
> AI：直接重写整个 `UserList.tsx`，顺手把状态管理从 `useState` 改成 `useReducer`，重命名了几个变量，删掉了一个"看起来没用"的辅助函数。

问题：改动范围失控，用户从 diff 里分不清哪些是搜索功能相关、哪些是 AI 顺手做的，审查成本极高，还可能引入未预期的 bug。

**✅ 正例**

> 用户："帮我在用户列表加一个搜索功能"
>
> AI：
> ```
> 📋 变更方案
> 目标：在 UserList 组件中新增按用户名搜索的功能
> 范围声明：仅修改 UserList.tsx，新增搜索框和过滤逻辑
> 实现思路：① 新增 searchQuery 状态 ② 新增搜索框 UI ③ 渲染前按 name 过滤列表
> 不在范围内：不改动现有状态管理方式、不调整现有样式
> 请确认是否继续？
> ```
>
> 用户："可以"
>
> AI：（只新增约 15 行代码，不改动无关逻辑）
> ```
> ✅ 变更汇报
> 改动文件：UserList.tsx —— 新增搜索框和过滤逻辑（约 15 行）
> 验证方式：本地运行，输入关键字确认列表正确过滤
> ```

## 五、提交前快速自检清单

- [ ] 只改了任务范围内的代码，没有顺手改动
- [ ] 没有无意义的重命名 / 重构 / 格式化
- [ ] 保留了原有注释和无关逻辑
- [ ] 改动可以独立验证（测试通过 / 能正常运行）
- [ ] 已清晰汇报改了什么、为什么改
- [ ] 不确定的地方已经明说，没有靠猜测蒙混过关

---

## 六、配套建议

- 让 AI 开始工作前先 `git commit` 打一个检查点，方便随时 diff 或回滚；
- L 级任务建议开新分支，逐步 review 每一步改动，而不是等全部做完再看；
- AI 越权改动时，直接引用第一条"范围锁定"提醒它收敛；
- 如果某类越界行为反复出现，就把它写成本文档里的一条具体规则，而不是每次口头重复。
