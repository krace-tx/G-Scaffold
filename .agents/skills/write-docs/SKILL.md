# 文档编写思路 (Write Docs Skill)

> 文档给后来的人（含 Agent）快速看懂模块：它做什么、文件怎么摆、怎么调用。不写教程、不写百科。

核心思路：**先读代码再下笔**。只写当前实现里真有的行为，不写计划中的、猜的、或顺手扩的。

## 一、何时写

- 用户要求给某个 feature / service 写文档
- 新建模块文档、把 README 改成项目约定文件名
- 改文档结构或核心说明

## 二、文件命名与位置

- 文件名：snake_case，前缀 `_doc_`，后缀是所属 `{feature}` → `_doc_{feature}.md`（下划线前缀确保在 IDE 资源树中永远自然排在最顶层）
- 放在该 feature 目录下，不要用 `README.md`（避免和别处说明撞名）
- 示例：`persist_service/_doc_persist_service.md`、`assets/_doc_assets.md`

## 三、结构：总分总

顺序固定。块与块之间用 `---` 分割，每块一个 `##` 标题。写完样例就结束。

1. **总** → `## 核心`：先把模块一句话说清
2. **分** → `## 细节`：再摊开真正要用到的要点（含文件 graph）
3. **总** → `## 样例`：用最短调用把核心逻辑收束回去

```markdown
# {FeatureName}

## 核心

<总：一针见血阐述做什么、不做什么。只定性，不在这里列策略清单。>

---

## 细节

<分：比较重要的细节，一条一事。入口、默认链、副作用、边界。>

\`\`\`
<目录文件 graph，每个文件一行注释：职责>
\`\`\`

---

## 样例

\`\`\`gdscript
<总：最短可跑通的调用。读完样例应能回扣核心：谁调度、载荷从哪来、怎么写再怎么读。>
\`\`\`
```

不要再加配置表、FAQ、迁移说明、历史对比，除非用户点名要。

## 四、核心（第一个总）

只阐述，不展开。读者看完应知道「这模块管什么、不管什么」。

必须写清：

1. **做什么**：调度对象是谁、在哪几层、靠什么字段路由
2. **不做什么**：编解码、网络、业务校验若不属于本模块，写明边界

禁止把入口、默认策略、回灌、删除范围堆进核心段。那些放到 `## 细节`。

## 五、细节与样例

**细节（分）**

- 入口：谁创建、调用前要绑什么
- 默认路径与副作用：默认读/写链、回灌范围、删除碰不碰远端
- 一条一事，不把读/写/删塞进同一句
- 字段、类型、策略名用代码里的真名（如 `key_id`、`CACHE_FIRST`、`Dictionary`）
- 空路径跳过、只清本地、不回写远端这类边界要写，不要靠读者猜
- 架构画实际目录树。每个文件一行职责；死代码、未使用目录不要画进去

**样例（第二个总）**

- 不是又一篇教程，是把核心逻辑用代码再讲一遍
- 从现有测试或真实调用抄最短路径：bind → encode → write → read → decode
- API 名必须能在代码里搜到。不要虚构演示类型，除非该模块已有对应实体

## 六、禁止

- 把文档写成逐步教程（改 CSV、点项目设置、切语言那种）
- 复述每个函数的参数表（那是代码注释的事）
- 在文档里发明尚未落地的 API
- 为了「完整」把无关模块写进来
